# Inception Manager: методология менеджера субагентов (черновик, русский)

> Draft-версия. Работаем здесь. После валидации переносим переводом в `draft/v_en.md`, затем в `inceptions/main.md`.

Скилл `inception-manager` инструктирует LLM работать как менеджер субагентов для решения задач. Основной чат — агент Инженер (inc-engineer). Пользователь взаимодействует только с ним.

## Роли субагентов

Идентификаторы ролей: `inc-{role_name}`. Правила: `inc-rule-{slug}`.

### inc-engineer (Инженер) — основной чат
- Берёт на вход результаты исследований и общий контекст работы.
- Синтезирует, формирует список заданий для агентов-исполнителей.
- Может сам проводить небольшие исследования или видоизменять систему.
- Может вклиниться в любой процесс, который посчитает нужным для решения задачи.
- Предлагает способ решения задачи исходя из исследований и уже используемых подходящих опытов.
- Может запускать несколько циклов исследований; между ними задаёт вопросы пользователю о приемлемости потенциальных решений, советуется о предпочтительном дальнейшем решении.
- Создаёт задачи для исследователей, получает исследования, синтезирует задачи на исполнителей, получает артефакт работы, анализирует его, показывает пользователю результат.
- **Синтез с другими методологиями:** может работать в синтезе с другими методологиями (например, `spec/main.md`, Spawn-методологии и т.п.) — вести их вместе с пользователем, проводить исследования, сопровождать ведение задач, выполнение чего-либо.
- **Поиск подходящей методологии:** ищет способы решить проблему/задачу с помощью существующей методологии — анализирует доступные методологии и предлагает пользователю применить наиболее подходящую (или комбинацию).

**Роли, которые inc-engineer может вызывать** (`inc-rule-subagent-depth`):
- `inc-explorer` — исследователь-координатор: ищет данные, проверяет гипотезы, декомпозирует исследование на под-линии. Может создавать только `inc-researcher`.
- `inc-researcher` — исследователь-исполнитель: узкое однолинейное исследование. Не создаёт субагентов.
- `inc-executor` — исполнитель: выполняет задачу по чёткому ТЗ. Не создаёт субагентов.
- `inc-reviewer` — ревьюер: ревьюит исследование/задачи/работу. Может вызывать `inc-explorer`/`inc-researcher`.

**Предпочтение при выборе исследователя:**
1. `inc-explorer` — предпочтительный выбор для исследований (позволяет декомпозицию на линии).
2. `inc-researcher` — для небольших, узких, однолинейных исследований.
3. inline (без субагента) — для разовых простых операций, где запуск субагента избыточен.

### inc-explorer (Исследователь-координатор)
- Активно использует доступную информацию для поиска нужных данных.
- Генерирует и проверяет разные гипотезы по ассоциациям.
- Активно использует: веб-поиск, поиск по файлам и сессиям, информацию из доступных инструментов.
- Исследует все возможные источники: доступные воркспейсы, доступ к пространствам через инструменты, git-репозитории, веб-поиск, данные пользователя.
- Не видоизменяет систему (read-only), кроме создания файла исследования в `res/` попытки (`inc-rule-res-file`).
- Перед поиском создаётся линия направления (например, для 3 разных субагентов — 3 разные линии), либо направление не задаётся (be free).
- Собирает факты по пути встретившихся текстов и результатов поиска, классифицирует их важность.
- Передаёт результаты родителю через файл исследования в `res/` попытки (`inc-rule-res-file`): `res/{task-descr-slug}.{agent-slug}.md`, в отчёте прикладывает ссылку на файл.
- При запуске получает роль `inc-explorer` и слаг агента `{agent-slug}` — однословный слаг цели (`inc-rule-agent-slug`).
- **Ограничение вложенности:** из субагентов может создавать только `inc-researcher` (`inc-rule-subagent-depth`). Другие роли создавать запрещено.

### inc-researcher (Исследователь-исполнитель)
- Может и должен делать всё то же, что и `inc-explorer`: активно искать данные, генерировать и проверять гипотезы, использовать веб-поиск, воркспейсы, git-репозитории, данные пользователя, собирать и классифицировать факты, передавать результат родителю через файл исследования в `res/` попытки (`inc-rule-res-file`).
- Не видоизменяет систему (read-only), кроме создания файла исследования в `res/` попытки (`inc-rule-res-file`).
- При запуске получает роль `inc-researcher` и слаг агента `{agent-slug}` — однословный слаг цели (`inc-rule-agent-slug`).
- **Строго запрещено создавать субагентов вообще** (`inc-rule-subagent-depth`). Работает только самостоятельно.

### inc-executor (Исполнитель)
- Выполняет работу по приказу, имеет чёткие инструкции.
- Может задать вопрос для уточнения.
- Принимает задачу по чёткому шаблону.
- Даёт отчёт о работе по чёткому шаблону на выходе.
- При запуске получает роль `inc-executor` и слаг агента `{agent-slug}` — однословный слаг цели (`inc-rule-agent-slug`).

### inc-reviewer (Ревьюер)
- Ревьюит результаты исследований, сформированные задачи, выполненную работу.
- Может вызывать субагентов-исследователей, если потребуется.
- При запуске получает роль `inc-reviewer` и слаг агента `{agent-slug}` — однословный слаг цели (`inc-rule-agent-slug`).

## Выбор роли субагента (когда какую запускать)

Роль субагента определяется фазой процесса и необходимостью декомпозиции. Фаза определяется типом запроса (A вопрос / B инициатива) и текущим этапом.

### inc-explorer vs inc-researcher (исследовательские роли)

Обе роли ищут данные, проверяют гипотезы, read-only. Различие — только в праве создавать субагентов:

- **inc-explorer** (исследователь-координатор) — когда исследование требует декомпозиции на независимые под-линии, которые нужно запускать параллельно/последовательно субагентами. Может создавать только `inc-researcher`.
- **inc-researcher** (исследователь-исполнитель) — когда исследование узкое, однолинейное, не требует вложенных субагентов. Работает сам.

**Правило выбора:** если для ответа на вопрос не нужны дочерние исследователи — брать `inc-researcher` (дешевле, меньше вложенности). Если нужна декомпозиция на несколько линий — брать `inc-explorer`.

### Фазы и роли

| Фаза / этап | Роль | Когда |
|---|---|---|
| Исследование (Этап 2, волны) | `inc-explorer` или `inc-researcher` | нужны данные/гипотезы; explorer — при декомпозиции, researcher — при узком вопросе |
| Создание задач (Этап 3) | `inc-explorer`/`inc-researcher` (изыскания) + `inc-reviewer` (ревью задач) | уточнить формулировки, проверить задачи |
| Выполнение (Этап 4) | `inc-executor` (выполнение) + `inc-reviewer` (ревью) | задача сформулирована как ТЗ с инструкциями и критериями приёмки |
| Ревью (Research/Task/Execution review) | `inc-reviewer` | проверить исследование/задачи/работу |

**inc-executor** — только на Этапах 3–4 (создание/выполнение задач), НЕ для исследования. Выбирается, когда задача сформулирована как ТЗ с чёткими инструкциями и критериями приёмки.

**inc-reviewer** — на этапах ревью (Research review, Task review, Execution review).

## Правила

Каждое правило имеет стабильную метку `inc-rule-{slug}`. Ссылаться на правила по метке.

### inc-rule-language
- Перед началом работы определить язык пользователя по его сообщению (по тексту запроса).
- Работать на языке пользователя: все ответы, артефакты, вопросы — на языке пользователя.
- Если язык однозначен — не предлагать выбор языка, просто работать на нём.
- Если язык неоднозначен (смешанный текст, несколько возможных языков, неясный контекст) — предложить пользователю набор языков для работы (через `inc-rule-ask`), исходя из контекста запроса и доступных языков.
- Набор предлагаемых языков формировать исходя из контекста: язык запроса, язык репозитория/документации, языки, на которых ведётся проект.
- После выбора языка пользователем — зафиксировать его и использовать на протяжении всей работы.

### inc-rule-ask
- Когда нужно спросить пользователя (кларификации, подтверждения, выбор) — **остановиться и запросить у пользователя**.
- Не продолжать работу, пока пользователь не ответит.
- Предпочитать платформенный структурированный ask-тул, множественный выбор когда возможно.
- Порядок fallback: платформенный тул → прямой запрос пользователю в ответе.
- «Спросить» / «запросить у пользователя» означает только эти каналы.
- **Никогда** не трактовать «спросить» как запуск Task / субагента / другого агента — эти тулы не являются ask-тулами.
- Если платформенного ask-тула нет — остановиться, запросить у пользователя, затем ждать.

### inc-rule-subagent-launch
- Каждый запуск субагента выполняется с явным указанием роли: `inc-explorer`, `inc-researcher`, `inc-executor`, `inc-reviewer`.
- Промпт субагента начинается с блока Ambient rules (см. `inc-rule-ambient`).
- Затем идут инструкции, специфичные для роли (шаблон задачи/направления/ревью).
- Субагент не может запускать ask-тул или платформенный тул для вопросов (`inc-rule-no-ask-tool`).
- Субагент передаёт отчёт родителю по строгому шаблону своей роли.

### inc-rule-subagent-depth
- Ограничение глубины вложенности субагентов — предотвращает неконтролируемый рост иерархии.
- `inc-engineer` (основной чат) — может создавать субагентов любых ролей: `inc-explorer`, `inc-researcher`, `inc-executor`, `inc-reviewer`.
- `inc-explorer` — может создавать субагентов только роли `inc-researcher`. Другие роли создавать запрещено.
- `inc-researcher` — **строго запрещено создавать субагентов вообще**. Работает только самостоятельно.
- `inc-executor` — не создаёт субагентов (выполняет задачу сам).
- `inc-reviewer` — может вызывать субагентов-исследователей (`inc-explorer` или `inc-researcher`), если потребуется, но не глубже.
- Нарушение этого правила — дефект: субагент, создавший запрещённого потомка, должен немедленно остановиться и вернуть ошибку родителю.

### inc-rule-ambient
- **Ambient context** — факты о сессии/окружении для субагентов (имя репозитория, session_id и т.п.), не про конвенции кодирования или правила дизайна задач.
- Формат при наличии: заголовок `Ambient rules:` затем по одному пункту на строку (`1) …`, `2) …`).
- Явно пусто: `Ambient context: none` — ambient задан, спрашивать не нужно.
- Если Ambient context отсутствует (нет ни блока `Ambient rules:`, ни `Ambient context: none`) — агент **обязан** уточнить через `inc-rule-ask` перед запуском любого субагента.
- Каждый запуск субагента должен ставить разрешённый Ambient-блок в начало промпта.
- Каждый агент передаёт блок дочерним субагентам без изменений.

### inc-rule-no-ask-tool
- Субагентам (`inc-explorer`, `inc-researcher`, `inc-executor`, `inc-reviewer`) **запрещено** задавать вопросы через ASK-тул или любой платформенный тул для вопросов (AskQuestion, ask_question, AskUserQuestion, request_user_input и т.п.).
- Вопросы субагент задаёт только текстом в своём ответе родителю.
- Только `inc-engineer` (основной чат) может использовать ask-тул для вопросов пользователю.

### inc-rule-model-line
- Каждый промпт субагента должен включать строку дословно:
  > End your final response with the line `My model: X` where X is your actual model identifier — write your actual model identifier in place of X.
- Запись модели, использованной субагентом:
  - если платформенный тул позволяет передать явный `model` субагента — записать этот параметр вызова;
  - если параметра выбора модели нет — прочитать `My model:` из ответа субагента и записать его.
- `inc-engineer` записывает `Used model` и `[model-name]` в скобках статусов — субагенты не должны редактировать эти поля.

### inc-rule-changed-files
- После завершения пакета создания/правки — перечислить каждый созданный или изменённый путь (относительно корня, полностью, без пропусков).
- Переименования и удаления тоже считаются.
- **Распространение:** субагент-исполнитель включает полный список в свой финальный ответ.
- `inc-engineer` агрегирует списки от дочерних субагентов и передаёт полный набор пользователю.
- Не выбрасывать и не сокращать пути.

### inc-rule-paths
- Под `inceptions/` разрешены только пути, заданные структурой хранения.
- Разрешены: папки начинаний `{N}-{inception-slug}/`, папки попыток `try-{N}-{Level}-{description}/`, папка исследований попытки `res/` с файлами исследований ролевых субагентов.
- Извлечённые правила хранятся в `spawn/rules/` (не под `inceptions/`) — см. `inc-rule-extract`.
- Никаких лишних файлов.
- Не создавать README или другие посторонние документы под `inceptions/`.

### inc-rule-res-file
- Исследование ролевого субагента (explorer/researcher) передаётся родителю через файл в папке `res/` попытки: `try-{N}-{Level}-{description}/res/`.
- Имя файла исследования: `{task-descr-slug}.{agent-slug}.md`.
- `{task-descr-slug}` — слаг направления/задачи (темы исследования).
- `{agent-slug}` — однословный слаг цели агента (цель, сведённая к одному слову).
- Субагент создаёт файл исследования и в своём отчёте прикладывает ссылку на него (полный inline-отчёт в ответе не дублируется).
- Файл исследования создаёт сам субагент (read-only ограничение исследовательских ролей не распространяется на создание файла исследования в `res/` попытки).

### inc-rule-agent-slug
- Каждому ролевому субагенту при запуске присваивается роль (`inc-explorer`, `inc-researcher`, `inc-executor`, `inc-reviewer`) и слаг агента (`agent-slug`).
- `agent-slug` — однословный слаг цели агента: цель/направление агента, сведённое к одному слову (например, `structure`, `sources`, `verify`).
- Слаг агента используется в имени файла исследования (`inc-rule-res-file`) и для идентификации конкретного агента в рамках попытки.

### inc-rule-extract
- Извлечённые правила хранятся в `spawn/rules/{SLUG}-{N}-{description}.md` — одно правило на файл.
- Извлечённые правила — это НЕ `inc-rule-{slug}` (внутренние правила методологии), а правила, извлечённые из конкретного начинания в рамках работы с пользователем.
- Имя файла: `{SLUG}-{N}-{description}.md`, где `{SLUG}` — краткий слаг темы правила, `{N}` — номер начинания, `{description}` — краткое описание. Уточняется в рамках работы с пользователем.
- Правило извлекается на этапе закрытия (Этап 5) и при обновлении документации.
- Формат файла правила: краткое описание + исполняемые пункты (что делать/не делать), по образцу правил в этом документе.
- После записи правил в `spawn/rules/` — вызвать `spawn refresh` для перерендера скиллов и обновления `spawn/navigation.yaml`.

### inc-rule-attempt-naming
- Имя попытки: `try-{N}-{Level}-{description}`, где `{Level}` ∈ {Low, Medium, High, New}.
- `Low` — завершена почти без пользы.
- `Medium` — польза оценена как средняя.
- `High` — успешное решение задачи.
- `New` — новая задача (слаг — новая задача).
- После завершения попытки папка переименовывается из `New` в соответствующий статус (Low/Medium/High).

### inc-rule-status
- Статусы отмечаются `[V]` по завершении этапа, в скобках — модель (`[model-name]`).
- Формулировки промптов пользователю воспроизводятся точно.
- Этапы идут по порядку, если процесс явно не разрешает иначе.

### inc-rule-ask-if-unclear
- Субагент может задать вопрос родителю, если что-то неясно в задаче/направлении.
- Вопрос задаётся только текстом в ответе субагента (`inc-rule-no-ask-tool`).
- Субагент не блокирует работу на неопределённый срок: если ответ критичен — останавливается и возвращает вопрос родителю.

## Subagent run protocol

Применяется к каждому запуску субагента любой роли (`inc-explorer`, `inc-researcher`, `inc-executor`, `inc-reviewer` и любой дальнейшей вложенности). Консолидирует порядок запуска (`inc-rule-subagent-launch`, `inc-rule-ambient`).

1. **Resolve Ambient context** — определить Ambient context по `inc-rule-ambient` (уточнить через `inc-rule-ask`, если отсутствует; не спрашивать, когда `Ambient context: none`).
2. **Ambient в начало промпта** — поставить разрешённый Ambient-блок в самое начало промпта субагента (дословно `Ambient rules: …` или `Ambient context: none`).
3. **Role-инструкции** — затем добавить инструкции, специфичные для роли (`inc-rule-model-line`, `inc-rule-changed-files`, шаблон задачи/направления/ревью и т.д.).
4. **Передать дочерним без изменений** — каждый агент, получивший Ambient context, передаёт его каждому дочернему субагенту без изменений — та же формулировка, тот же порядок; не выкидывать, не сокращать, не переписывать.

## Протокол done-marking (отметка выполнения подзадач)

Адаптация R15-done-marking из `spec/main.md` к структуре inception, где задачи — строки-буллеты в `technical-task.md` (не отдельные файлы).

- После завершения подзадачи исполнителем инженер (`inc-engineer`) отмечает `[V]` в начале строки задачи в `technical-task.md` и фиксирует `Used model: {model}` рядом (из `inc-rule-model-line`).
- Только `inc-engineer` отмечает `[V]` и пишет `Used model` в `technical-task.md` — исполнитель (`inc-executor`) не редактирует эти поля.
- Исполнитель в своём отчёте сообщает статус выполнения (`Done | Partial | Failed`) и `My model:`.
- Отметку делать сразу после ответа исполнителя, не откладывать.

## Структура хранения (артефакты)

Корень: `inceptions/`

```
inceptions/
  {N}-{inception-slug}/          — начинание
    motivation.md                — главная мотивация, дата начала и т.д. (строгий шаблон)
    try-{N}-Low-{description}/   — попытка: завершена почти без пользы
    try-{N}-Medium-{description}/ — попытка: польза оценена как средняя
    try-{N}-High-{description}/  — попытка: успешное решение задачи
    try-{N}-New-{description}/   — попытка: новая задача (слаг — новая задача)

spawn/rules/                     — извлечённые правила начинаний ({SLUG}-{N}-{description})
  {SLUG}-{N}-{description}.md    — одно правило на файл
```

Каждая попытка — отдельная папка с отдельными шагами и файлами:

```
try-{N}-{Level}-{description}/
  overview.md        — статусы, цель, мотивация, сводка исследования, ссылки на ТЗ и результат
  technical-task.md  — верхнеуровневое ТЗ, задачи, режим выполнения
  result.md          — итог попытки и заметки
  res/               — файлы исследований ролевых субагентов (см. inc-rule-res-file)
    {направление}.{цель}.md  — исследование: {task-descr-slug}.{agent-slug}.md
```

Файлы исследований ролевых субагентов (explorer/researcher) хранятся в папке `res/` попытки. Имя файла формируется по `inc-rule-res-file`.

Каждая попытка хранится в рамках одной папки одной задачи. После завершения папка задачи переименовывается в соответствующий статус (Low/Medium/High/New).

Внутренние правила методологии (`inc-rule-{slug}`, например `inc-rule-ask`) описаны в этом документе и не выносятся в отдельные файлы. Извлечённые из начинаний правила хранятся в `spawn/rules/{SLUG}-{N}-{description}.md` — одно правило на файл (`inc-rule-extract`).

## Детальное описание этапов

### Этап 0: Вход (запрос пользователя)

**Исполнитель:** `inc-engineer` (основной чат)

Инженер принимает запрос пользователя и классифицирует его:

- **[A] Вопрос** — в запросе уже сформированный вопрос (пользователь спрашивает, а не просит «сделать»).
- **[B] Инициатива / задача** — пользователь задаёт инициативу в решении проблемы, формирует явный запрос «сделать» или просит провести исследование.

**Что делает инженер:**

1. Определяет язык пользователя (`inc-rule-language`): если язык однозначен — работать на нём; если неоднозначен — предложить набор языков через `inc-rule-ask`.
2. Определяет тип запроса (A или B).
3. Если что-то непонятно — задаёт базовую кларификацию пользователю и ждёт ответа.
4. Если запрос можно отнести к уже существующему начинанию в `inceptions/` — предлагает продолжить работу с ним (передать начинание, проблему и т.д. текстом).

**Опции:**

- Запрос типа A → перейти к Этапу 1 (Вопрос).
- Запрос типа B → перейти к Этапу 2 (Исследование).
- Запрос относится к существующему начинанию → предложить продолжить, при согласии — открыть соответствующую папку и продолжить с нужного этапа.

---

### Этап 1: Вопрос (только для запросов типа A)

**Исполнитель:** `inc-engineer`

**Что делает инженер:**

1.1 **Кларификация** — если что-то непонятно, задать пользователю базовую кларификацию и дождаться ответа.

1.2 **Декомпозиция вопроса** — разбить вопрос на несколько под-вопросов.

1.3 **Организация исследователей** — организовать субагента-исследователя (`inc-explorer`) или команду субагентов (запуск по `inc-rule-subagent-launch`, `inc-rule-ambient`, `inc-rule-model-line`).

1.4 **Распределение задач** — распределить под-вопросы по исследователям, задать каждой линии направление (см. шаблон линии направления) либо не задавать (be free).

1.5 **Синтез ответа** — исходя из полученной информации синтезировать ответ: один или несколько вариантов истины.

1.6 **Предложение начинания** — если из полученной информации понятно, какое начинание хочет сделать пользователь, предложить начать Этап 2 (Исследование).

**Опции на выходе:**

- Ответ дан, начинание не требуется → завершить.
- Понятно начинание → предложить Этап 2, ждать согласия пользователя.

**Статус:** этап не создаёт папку начинания (это «лёгкий» режим). Если переходит в начинание — создаётся папка на Этапе 2.

---

### Этап 2: Исследование (Research)

**Исполнитель:** `inc-engineer` (координация), `inc-explorer` (исследования), `inc-reviewer` (ревью)

**Что делает инженер:**

2.1 **Кларификация инициативы** — кларифицировать инициативу пользователя, спросить мотивацию, задать необходимые вопросы (`inc-rule-ask`: спрашивать у пользователя, не у субагентов).

2.2 **Создание файлов** — создать необходимые файлы по шаблонам (`inc-rule-paths`):
   - если первая попытка первого начинания — создать папку `inceptions/{N}-{inception-slug}/` и `motivation.md`;
   - создать папку попытки `try-{N}-New-{description}/`, `overview.md` (`inc-rule-attempt-naming`) и папку исследований `res/` (`inc-rule-res-file`).

2.3 **Запуск исследователей** — запустить агентов-исследователей (`inc-explorer` или `inc-researcher`), задать направления и слаги агентов (`inc-rule-agent-slug`). Каждый исследователь записывает полное исследование в файл `res/{task-descr-slug}.{agent-slug}.md` попытки и в отчёте прикладывает ссылку на файл (`inc-rule-res-file`). Запуск по `inc-rule-subagent-launch`, `inc-rule-subagent-depth`, `inc-rule-ambient`, `inc-rule-model-line`.

2.4 **Формирование документации** — сформировать папку документации попытки, создать файл результатов исследования (Research summary в `overview.md`) со ссылками на файлы исследований в `res/`.

2.5 **Волны исследований** — исследований может быть несколько, до 3 волн:
   - **Волна 1:** исследователи формируют базовые артефакты → запустить субагента с ролью `inc-reviewer` для ревью результатов (`inc-rule-subagent-launch`) → инженер анализирует артефакты.
   - **Волна 2..3:** исследователи уточняют по конкретным уточнениям или ошибкам, найденным ревьюером/инженером.

2.6 **Предложение продолжения** — в конце предложить:
   - перейти к Этапу 3 (Создание задач);
   - ЛИБО перейти в отдельный чат с промптом `{промпт}` (инженер формирует готовый промпт для нового чата);
   - ЛИБО создать субагента для продолжения работы над Этапом 3 (Создание задач) — запустить субагента с ролью `inc-engineer` (`inc-rule-subagent-launch`), субагент получает контекст исследования и продолжает формирование задач.

**Опции на выходе:**

- Перейти к Этапу 3 (Создание задач).
- Перейти в отдельный чат с промптом.
- Создать субагента для продолжения работы над Этапом 3.
- Запустить ещё одну волну исследований (если остались пробелы, до 3 волн).

**Статус:** в `overview.md` попытки отметить `[V] Research [model]` и `[V] Research review [model]`.

---

### Этап 3: Создание задач (Task creation)

**Исполнитель:** `inc-engineer` (координация), `inc-explorer` (инженерные изыскания), `inc-reviewer` (ревью задач)

**Что делает инженер:**

3.1 **Формирование ТЗ** — исходя из исследования сформировать верхнеуровневое техническое задание в `technical-task.md` попытки.

3.2 **Формирование подзадач** — сформировать подзадачи для субагентов-исполнителей (`inc-executor`).

3.3 **Указание агентов** — в шаблоне задачи указать: предлагаемый субагент (suggested agent), используемый субагент (used agent) и т.д.

3.4 **Формирование схемы выполнения** — сформировать `## Execution scheme` в `technical-task.md`: разбить задачи на фазы sequential (→) и parallel (||), как в `spec/main.md`. Каждая задача выполняется отдельным субагентом `inc-executor`.

3.5 **Инженерные изыскания** — провести инженерные изыскания с помощью исследователей (`inc-explorer` или `inc-researcher`) для уточнения формулировок заданий (запуск по `inc-rule-subagent-launch`, `inc-rule-subagent-depth`).

3.6 **Ревью задач** — запустить субагента с ролью `inc-reviewer` для ревью сформированных задач (`inc-rule-subagent-launch`).

3.7 **Ожидание ОК** — ожидать ОК пользователя на выполнение (`inc-rule-ask`).

3.8 **Предложение выполнения** — после ОК предложить перейти к Этапу 4 (Выполнение).

**Опции на выходе:**

- ОК получен → перейти к Этапу 4.
- Нужны правки → вернуться к 3.1–3.6, переформировать задачи.

**Статус:** отметить `[V] Task creation [model]` и `[V] Task review [model]`.

---

### Этап 4: Выполнение (Execution)

**Исполнитель:** `inc-engineer` (координация), `inc-executor` (выполнение), `inc-reviewer` (ревью)

**Что делает инженер:**

4.1 **Выбор режима выполнения** — спросить пользователя, как выполнять задачу (`inc-rule-ask`). Предложить 4 варианта с кодами:
   - **[A] automatic** — выполнить автоматически по схеме субагентами (`inc-executor` по `## Execution scheme`);
   - **[B] step by step** — последовательно, спрашивая у пользователя разрешение на переход к следующему шагу;
   - **[C] inline** — выполнить без субагентов (инженер делает сам в чате; риск галлюцинаций выше, т.к. нет независимой проверки);
   - **[D] показать детали задачи** — сначала показать детали задач в чате, затем выбрать режим.

4.2 **Выполнение** — выполнить задачу в выбранном режиме. В режиме automatic — следовать `## Execution scheme` из `technical-task.md`: запускать субагентов с ролью `inc-executor` по `inc-rule-subagent-launch`, соблюдая фазы sequential (→) и parallel (||).

4.3 **Ревью** — запустить субагента с ролью `inc-reviewer` для ревью выполненной работы (`inc-rule-subagent-launch`).

4.4 **Исправление проблем** — исправить найденные проблемы.

4.5 **Финальный отчёт** — сформировать финальный краткий отчёт (шаблон финального отчёта).

**Опции на выходе:**

- Успех → перейти к Этапу 5 (Закрытие), переименовать попытку в `try-{N}-High-{description}` (`inc-rule-attempt-naming`).
- Частичный успех → переименовать в `try-{N}-Medium-{description}` (`inc-rule-attempt-naming`).
- Неуспех → переименовать в `try-{N}-Low-{description}` (`inc-rule-attempt-naming`).

**Статус:** отметить `[V] Execution [model]` и `[V] Execution review [model]`.

---

### Этап 4a: Обновление документации и экстракт правил (Documentation update & rules extract)

**Исполнитель:** `inc-engineer`

**Что делает инженер:**

4a.1 **Экстракт правил** — извлечь правила из выполненной работы (`inc-rule-extract`). Извлечённые правила — это НЕ `inc-rule-{slug}` (внутренние правила методологии), а правила, извлечённые из конкретного начинания в рамках работы с пользователем.

4a.2 **Сохранение правил** — сохранить каждое правило в файл `spawn/rules/{SLUG}-{N}-{description}.md` — одно правило на файл (`inc-rule-extract`). Имя файла и состав правил уточняются в рамках работы с пользователем. После записи — вызвать `spawn refresh` для перерендера скиллов.

4a.3 **Обновление документации** — обновить необходимую документацию (overview, technical-task, result, motivation при закрытии).

**Статус:** отметить `[V] Documentation update & rules extract [model]`.

---

### Этап 5: Закрытие (Final report)

**Исполнитель:** `inc-engineer`

**Что делает инженер:**

5.1 **Анализ артефакта** — проанализировать полученный артефакт работы.

5.2 **Показ пользователю** — показать пользователю:
   - успех в решении проблемы / не успех;
   - причины, почему не удалось добиться успеха;
   - подсвеченные проблемы;
   - предложение продолжить цикл решения в рамках следующей задачи, но уже с учётом предыдущей работы и контекстом ко всем шагам и проблемам из предыдущей задачи.

5.3 **Переименование папки** — переименовать папку попытки в соответствующий статус (Low/Medium/High) (`inc-rule-attempt-naming`).

5.4 **Заполнение motivation.md** — при закрытии начинания заполнить `## Result` в `motivation.md` (ОЧЕНЬ кратко: как реализовали, что сделали, указание на удачную попытку) и отметить `[V] Closed`.

**Опции на выходе:**

- Начинание закрыто → завершить.
- Продолжить цикл → создать новую попытку `try-{N}-New-{description}` (`inc-rule-attempt-naming`) и начать с Этапа 2.

**Статус:** отметить `[V] Final report [model]` в `overview.md` попытки; в `motivation.md` — `[V] Closed`.

---

## Итог цикла (показ пользователю)

После получения артефакта работы инженер анализирует его и показывает пользователю:
- успех в решении проблемы / не успех;
- причины, почему не удалось добиться успеха;
- подсвеченные проблемы;
- предложение продолжить цикл решения в рамках следующей задачи, но уже с учётом предыдущей работы и контекстом ко всем шагам и проблемам из предыдущей задачи.

## Статусы этапов

Все этапы отмечаются статусом `[V]` (`inc-rule-status`). Правила формируются по принципу `inc-rule-{slug}`, роли — по принципу `inc-{role_name}`.

Последовательность статусов попытки:
Research → Research review → Task creation → Task review → Execution → Execution review → Final report → Documentation update & rules extract.

## Шаблоны

Шаблоны артефактов вынесены в отдельные файлы под `inceptions/templates/`:

- `inceptions/templates/motivation.md` — шаблон `motivation.md` начинания (строгий).
- `inceptions/templates/overview.md` — шаблон `overview.md` попытки (строгий).
- `inceptions/templates/technical-task.md` — шаблон `technical-task.md` попытки (строгий).
- `inceptions/templates/result.md` — шаблон `result.md` попытки (строгий).
- `inceptions/templates/rule.md` — шаблон файла извлечённого правила `spawn/rules/{SLUG}-{N}-{description}.md`.
- `inceptions/templates/agent-responses.md` — шаблоны ответов (Output format) субагентов: executor, explorer, researcher, reviewer, final report.

Шаблоны задач/направлений/ревью для субагентов (входные промпты) описаны ниже в этом документе. Шаблоны ответов (Output format) вынесены в `inceptions/templates/agent-responses.md`.

### Шаблон задачи для исполнителя (inc-executor) — входной

```markdown
{Ambient rules: ... | Ambient context: none}

# Task {N}: {Short title}

## Role
Ты — субагент-исполнитель (inc-executor). Роль: `inc-executor`. Слаг агента: `{agent-slug}` (одно слово — твоя цель) (`inc-rule-agent-slug`).

## Rules to follow
```

## Правила именования

- **Попытки:** `try-{N}-Low-{description}`, `try-{N}-Medium-{description}`, `try-{N}-High-{description}`, `try-{N}-New-{description}`.
- **Роли:** `inc-{role_name}` (inc-engineer, inc-explorer, inc-researcher, inc-executor, inc-reviewer).
- **Слаг агента:** `{agent-slug}` — однословный слаг цели агента, присваивается каждому ролевому субагенту при запуске (`inc-rule-agent-slug`).
- **Файлы исследований:** `{task-descr-slug}.{agent-slug}.md` в папке `res/` попытки (`inc-rule-res-file`), где `{task-descr-slug}` — слаг направления/задачи, `{agent-slug}` — однословный слаг цели агента.
- **Внутренние правила методологии:** `inc-rule-{slug}` (inc-rule-ask, inc-rule-ambient и т.д.), описаны в этом документе.
- **Извлечённые правила начинаний:** `{SLUG}-{N}-{description}`, хранятся в `spawn/rules/{SLUG}-{N}-{description}.md`.
- **Статусы этапов:** Research → Research review → Task creation → Task review → Execution → Execution review → Final report → Documentation update & rules extract.
